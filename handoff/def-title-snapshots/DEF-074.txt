THE E2E FAILURE DIAGNOSTIC COULD NOT REACH THE FAILURE IT EXISTS TO EXPLAIN - `docker compose logs --tail 200` across NINE services covered about fifteen seconds, and the run it was asked about had failed six minutes earlier. Found 2026-08-15 on the first CI run with KEYCLOAK_ADMIN_ENABLED true (PR #278), while diagnosing a 500 from POST /api/members/me. MEASURED FROM THE RUN ITSELF, not inferred: the spec failed at 13:07:17, the Playwright retry finished at 13:11:59, the job's `Stack logs on failure` step ran at 13:12:01, and the OLDEST line the dump contained was timestamped 13:11:48. Every request in it returned 200. So the diagnostic printed a window of perfectly healthy traffic in answer to a question about a failure outside that window, and a reader skimming it would conclude the stack was fine. WHY IT IS THE SAME LESSON AS DEF-051 AND WORSE THAN NO DUMP AT ALL: DEF-051 recorded that a green check leaving no trace is how a broken reconcile shipped, and the fix there was to print the reconciler's log UNCONDITIONALLY. This is the second instance in the same workflow, with the twist that the output is not absent but MISLEADING - it reads like evidence. A dump that cannot contain the failure is a control that detects nothing while appearing to tell, which is the inverse of the recorded controls-must-detect-AND-tell finding. WHY 200 LINES WAS EVER ENOUGH AND IS NOT NOW: the number is shared across every service in the compose file, and the stack has grown to nine - api, web, worker, keycloak, keycloak-config, sql, minio, seq and ngrok. Seq alone writes an indexing line a minute, and the web nginx access log writes several lines per page load, so the api lines a reader actually needs are a small minority of the budget. The suite also got longer, which widens the gap between the failure and the dump. FIXED IN THE SAME PR: the api service is dumped SEPARATELY and FIRST at 4000 lines, because it is the service the specs assert against and interleaving it with eight others is precisely what made 200 lines cover seconds; the combined dump follows at 2000 lines for cross-service ordering. ⚠ THIS ROW IS ABOUT THE DIAGNOSTIC, NOT ABOUT THE 500. The underlying failure - POST /api/members/me returning 500 on the FIRST provisioning of a run, deterministic across the initial attempt and the retry, while every later call in the same run returned 200 - is a separate question whose cause is NOT YET ESTABLISHED and is deliberately not guessed at here. Reading ProvisionCurrentUserHandler shows it does not depend on IIdentityProvider at all, so the flag is not a direct cause; the leading hypothesis is a check-then-insert race between the SPA's own login-time provisioning and the test helper's explicit call, which can only collide on the FIRST login of a given subject and which moved to a new spec when this one became alphabetically first. That is a hypothesis awaiting the log this fix now makes available - it is written down so it can be checked and discarded, not so it can be assumed.
