AN INVITED GUEST PRESENTER GETS NO KEYCLOAK REALM ROLE, SO FR-159's GUEST CANNOT REACH THE GUEST SURFACE BUILT FOR THEM - /api/session/me ANSWERS 403 TO THE VERY PERSON IT EXISTS FOR. Found 2026-08-15 by the AC-011 live leg (PR #278), on the first occasion anyone has ever signed in as an invited guest. THE MEASUREMENT: with the guest created through the application's own endpoint and signed in through the real PKCE round-trip, GET /api/session/me returned 403 where the spec expected 200. GetMySessionQuery.AllowedRoles is Guest, Chairman, Secretary, so a principal actually holding Guest could not have been refused there. THE CAUSE, READ FROM THE CODE RATHER THAN INFERRED: MemberInvitation.InviteAsync - the single body both FR-156's InviteUser and FR-159's GuestProvisioner run - calls identity.CreateUserAsync and NOTHING ELSE. KeycloakAdminClient.CreateUserAsync creates the user and sets a temporary password; assigning realm roles is a SEPARATE method, SetRealmRolesAsync, which the invite path never calls. So the invited account exists in Keycloak with no realm role, its token carries no ACMP role claim, and every AllowedRoles check refuses it. THE LOCAL ROW AND THE IDENTITY DISAGREE, which is what makes this more than a missing call: InviteAsync is passed CommitteeRole.Guest and writes a committee_members row that says Guest, with an AccessExpiresAt window, so ACMP's own database believes this person is a guest presenter with timed access while Keycloak believes they are nobody. Every control downstream reads the token, not the row. ⚠ THE ROLE-LESS INVITE IS DELIBERATE FOR FR-156 AND WAS CARRIED INTO FR-159 BY REUSE, and the evidence that this was not intended is in the code's own words: InviteGuestPresenter's comment contrasts itself with FR-156 - 'That invite creates an inert account with no role; this one hands an EXTERNAL person real read access to unpublished committee material'. The author knew the shared body creates an inert account and stated that this use case is different, but the shared body is what runs, so FR-159 inherited exactly the behaviour the comment says it is not. An FR-156 invitee is meant to be inert until an administrator assigns roles (AssignRoles calls SetRealmRolesAsync); a guest presenter has no such follow-up step anywhere - the Secretary's single action is supposed to be sufficient. CONSEQUENCES, all of which follow from the same fact: (1) AC-011 cannot be satisfied as written, because the guest cannot reach the session that scopes them; (2) GuestSurfaceMiddleware.IsGuestOnly returns FALSE for this principal - they are not in role Guest - so the deny-by-default gate does not even classify them as a guest, and they fall through to the ordinary authenticated surface where each route's own policy decides; (3) ProvisionCurrentUser throws ForbiddenAccessException for them, since CommitteeRoleResolver.PrimaryRole returns null - the AC-003 deny path, reached here by a second route; (4) AuthorizationBehavior emits Authorization.Forbidden for their refused requests, which is why role-matrix.spec.ts's deliberate test.fail() for AC-006 reported 'Expected to fail, but passed' on this run - a CROSS-TEST COUPLING worth knowing about, since that marker is meant to flip when DEF-056 lands and it flipped for an unrelated reason. ⚠ NOT FIXED, BECAUSE THE FIX IS A DECISION RATHER THAN A LINE. The obvious change - have MemberInvitation assign the realm role matching the CommitteeRole it is given - would also change FR-156, whose inert-until-assigned behaviour is deliberate and is what AssignRoles exists for. OPTIONS: (a) assign the realm role only on the GUEST path, so GuestProvisioner passes the role through and InviteUser keeps creating an inert account; (b) assign for both and drop the inert-invite design, which is a larger change to FR-156 and to ADR-0038's flow; (c) require a separate role assignment after a guest invite, which contradicts DEC-037's premise that the Secretary's single action from the meeting screen is the whole use case. (a) is the narrow reading of ADR-0040 and does not disturb FR-156, but it is a scope decision on the operator's side and needs an SC- row.
