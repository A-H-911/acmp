JIT PROVISIONING HAS A CHECK-THEN-INSERT RACE: POST /api/members/me IS DOCUMENTED IDEMPOTENT AND IS NOT, UNDER CONCURRENCY. Two simultaneous calls for a subject with no member row both INSERT and the loser gets a 500. Found 2026-08-15 on the AC-011 e2e leg (PR #278) and MEASURED FROM THE API LOG, not inferred: `Microsoft.EntityFrameworkCore.DbUpdateException ... Cannot insert duplicate key row in object 'membership.committee_members' with unique index 'IX_committee_members_KeycloakUserId'`, logged twice for the same subject id within the same second, each surfacing as `HTTP POST /api/members/me responded 500`. THE MECHANISM, read from ProvisionCurrentUserHandler: it does FirstOrDefaultAsync on KeycloakUserId, and when that returns null it constructs CommitteeMember.Provision and Adds it, then SaveChangesAsync. Two requests interleaved between the read and the write both see null, both Add, and the unique index refuses the second. WHY IT HAD NEVER FIRED BEFORE: it can ONLY collide on the FIRST provisioning of a given subject, because every later call finds the row and takes the SyncFromClaims path where no insert happens. In e2e the first login of a run was historically driven by ac043-reorder.spec.ts, which uses loginAs plus captureBearer and NEVER calls meMember - so exactly one provisioning call was in flight, the SPA's own. ac011-guest-scope.spec.ts is the first spec to call roleSession at the START of a run, which adds an EXPLICIT second POST. The race was always present and had simply never been occupied. THE HARNESS IS NOT THE DEFECT: apiHelpers calls this endpoint deliberately as a guard against racing the SPA's async provision, which is a legitimate use of a contract the endpoint advertises and did not keep. The SPA's useRef guard means one call per mount, but two tabs opened together on a user's very FIRST login race the same way - the worst moment for it. BLAST RADIUS is small - one request, first login only, and a refresh succeeds because by then the winning row exists - which is why this is medium rather than high. ⚠⚠ CORRECTION 2026-08-15, AND IT IS A CORRECTION TO MY OWN ANALYSIS ON THIS ROW. This row previously asserted that the fix HAD to retry the whole command ABOVE TransactionBehavior, because catching the DbUpdateException inside the handler would leave a doomed ambient transaction. THAT WAS WRONG, and it was wrong in the way this project keeps recording: it was reasoned from a plausible premise instead of checked. A unique-key violation on SQL Server aborts the STATEMENT, not the transaction - XACT_ABORT is off - so the ambient transaction opened by this command is intact afterwards and TransactionBehavior commits it normally. Nothing partial was written either, because the failed insert was a single statement, which is what makes the MARS savepoint warning irrelevant here rather than fatal. THE SECOND FACT THAT MAKES A LOCAL RECOVERY CORRECT, and it is the one that matters most: SQL Server does not fail the loser's insert immediately - it BLOCKS on the winner's exclusive key lock and raises the duplicate only once that transaction has COMMITTED. So at the moment the loser lands in the catch, the winning row is committed and readable, and the loser's re-read is GUARANTEED to find it rather than merely likely to. FIXED IN PR #279 (fix/def-075-provisioning-race), and the fix is small because of the two facts above: the loser detaches its own pending insert (DbSet.Remove on an Added entity detaches it), re-reads, adopts the winner's row, syncs claims onto it and saves. A DbUpdateException with NO winning row behind it is rethrown unchanged, so the recovery is scoped to the one situation it understands and every other write fault on this path stays as loud as it was. ⚠ THE LOSER MUST NOT EMIT Membership.MemberProvisioned - only one of the two requests provisioned anybody, and the audit chain is append-only (INV-005), so a loser claiming provisioning writes a permanent row asserting an event that did not occur. FOUR TESTS, EACH MUTATION-PROVEN with the mutant confirmed to compile: removing the recovery kills 3, removing the detach kills 1 (the loser re-submits its own insert and a second row appears), absorbing a non-race failure kills 1, and letting the loser still report created kills 1. ⚠ THE RACE IS SIMULATED, NOT RUN, AND DELIBERATELY SO: the InMemory provider does not enforce unique indexes, so a genuinely concurrent test there would pass whether or not the fix existed - the exact DEF-066 shape. The tests reproduce the STATE THE LOSER FINDS ITSELF IN. The SQL-Server-side half is proven where it can only be proven: by the AC-011 e2e leg on a real database, which is what produced this defect. THIS ROW CLOSES WHEN #279 MERGES AND #278's e2e GETS PAST PROVISIONING - not on the fix being written.
