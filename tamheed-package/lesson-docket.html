Before you read

An approved lesson is immutable. The store refuses an edit to one — a change means writing a new lesson that supersedes it. So approving is the expensive direction, and rejecting costs nothing but the row.

Approving is not the same as agreeing a finding happened. These sentences were written by the agent, not by you. Selecting a finding is not approving the wording it was written up in.

  • Approve and pin — binds every future session and is written into the note the agent loads at startup. Reserve it for the ones worth interrupting someone with.
  • Approve — binds, but stays out of the startup note.
  • Reject — the row stays as history and binds nothing.
  • Refine — tell me what is wrong with the sentence and I will rewrite it for another pass.

The lesson

A work row that quotes its requirement accurately can still be wrong, because the REQUIREMENT is what a decision superseded. Nothing mechanical can see it: the ids resolve, the statuses are right, the trace gate passes, and the registers agree with each other - they simply agree about a sentence that a decision overruled. So sweep the ADR and DECISION registers before sizing, not only the requirement register. And where an ADR names the rows it undertook to amend, TREAT THAT LIST AS A CHECKLIST and compare it against every row that quotes the ADR's subject: the row the follow-through missed is the one still asserting the superseded text.

What happened

WBS-24.6 (DW-035 / FR-154), 2026-08-27, before any code was written. The WBS item, the deferred-work row and the requirement all said the audit-log export is *"accessible only to Auditor and Administrator"*. ADR-0027 (Approved) decides that audit read, search, EXPORT and delete are {Auditor, Chairman, Secretary} with Administrator EXCLUDED on segregation-of-duties grounds, and it names exporting explicitly. Building to the row's own text would have reversed an Approved ADR and broken control C-INS-03 - trap 32's shape, but arriving through a row that was not careless: it was a correct citation.

WHY EVERY INSTRUMENT PASSED. count-prompt-ids.py resolved all 271 cited identifiers and read every status correctly. The inline prose-status checker found nothing. G-TRACE passed. The requirement register was internally consistent. The fault is not a dangling id, a wrong status, or a missing link - it is a true sentence whose source died.

WHAT ACTUALLY CLOSED IT. Trap 32 / LL-008 got me into the ADR register, but that alone only produces a candidate. ADR-0027's own text records its follow-through: it states that FR-151 and FR-153 will carry a pointer to it. Both do, as relates_to edges. FR-154 had neither the pointer nor the edge - it was a Phase-2 requirement when the ADR was written and was simply missed. The ADR's promise about itself was the discriminator, and it is cheap to check.

The code had implemented the ADR correctly on both sides for months (Policies.AuditRead and the App.tsx route gate); only the register was out of step. DEC-081 d2 and SC-036 reconciled it before any code was written.

What to do instead

Before sizing a work item, read the ADR and DECISION registers for the row's subject as well as the requirement register (LL-008, trap 32). Then, for every ADR that turns out to govern it, read the ADR's OWN text for a list of rows it said it would amend or annotate - and check each one actually carries the pointer or the trace edge. Any row on that list without it is still asserting the superseded text, and any row NOT on that list that quotes the same subject was never considered at all.

Why it generalises

The failure mode is invisible to every mechanical control this package has, because none of them compares a requirement's text against a decision that overruled it - they check identifiers, statuses and link existence, all of which are correct here. The ADR's own follow-through list is the only artifact that already names the affected set, so it converts an open-ended 'read everything' sweep into a finite checklist.

If followed

A row whose requirement clause is dead is caught during sizing, before code is written, at the cost of reading one ADR. Here that prevented building an authorization surface that would have reversed an Approved ADR and defeated a segregation-of-duties control on the audit log - the one dataset whose access rules exist to constrain the platform's own operator.

If ignored

The build follows a row that reads correct, cites correctly, and passes every gate, while silently reversing a settled architectural decision. Nothing reports it: the code and the register would then agree with each other and both disagree with the ADR, which is the configuration hardest to detect later because the disagreement has no witness.
