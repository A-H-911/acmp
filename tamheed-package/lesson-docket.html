LL-026 improve testing Proposed

A test that asserts an ABSENCE straight after a framework lifecycle call is asserting against work the framework may not have done yet - and a runtime upgrade can empty it silently, because a negative assertion is true over an empty execution.

The lesson

When a test invokes a framework lifecycle method and asserts immediately afterwards, it is asserting against work the framework has not promised to have finished. If the assertion is NEGATIVE - nothing was received, nothing threw, no rows were written - it holds identically whether the code under test ran and correctly did nothing, or never ran at all. Which of those is happening is decided by the framework's scheduling, an implementation detail that changes between versions, so the test can be emptied by an upgrade while still passing. Only an instrument that measures EXECUTION rather than OUTCOME can tell the two apart.

What happened

The `net8.0` to `net10.0` migration, `DW-080` phase A, 2026-08-28 (`DEF-113`). `WebexWebhookRegistrarTests` called `IHostedService.StartAsync` and then asserted `api.DidNotReceiveWithAnyArgs()`. .NET 10's documented breaking change *BackgroundService runs all of ExecuteAsync as a Task* moved the whole method body onto a background thread, where .NET 8 had run everything before the first await inline on the caller. `ExecuteTask` read `WaitingForActivation` with no exception; a positive assertion in the same place failed with *"Actually received no matching calls"*. The test passed on BOTH runtimes and the suite was 1167 green either way. The sole signal was the per-file coverage floor putting the file at 92.00% (23/25) - two lines of a three-line method - which reads exactly like an attribution artefact and invites an exclusion or a lower threshold, either of which deletes the evidence.

What to do instead

Join deterministically before asserting: for a `BackgroundService` that is `StopAsync`, which awaits the stored `ExecuteTask`, and `StartAsync` is not a join at all. Then assert the POSITIVE observable the path produces rather than the absence of one, so the assertion has something to be false about. And when a per-file coverage floor names lines inside a method whose test passes, get the LINE NUMBERS and read them before concluding the instrument is miscounting - the hit COUNTS on the surrounding lines usually adjudicate on their own, by accounting exactly for the callers you can name.

Why it generalises

A negative assertion carries no information about whether the code executed, because it is satisfied by the empty run. The test suite therefore cannot distinguish a correct no-op from a no-op that never started, and no amount of adding assertions of the same shape will fix that. Coverage is the only routine instrument that measures execution rather than outcome, which is exactly why a per-file floor discriminated where 1167 passing tests could not - and why the two remedies the number invites, an exclusion or a lower threshold, would have removed the only working signal while leaving the vacuous test in place.

If followed

The lifecycle path is proven to run, and a future runtime upgrade that changes scheduling fails loudly at an assertion instead of quietly emptying the test. The coverage floor keeps its power to detect the class.

If ignored

A framework upgrade converts a passing test into one that exercises nothing, and the only evidence is a coverage figure that looks like an artefact of the new toolchain - so the cheapest-looking fix suppresses the measurement and enshrines the empty test permanently.

LL-027 improve verification Proposed

A valid argument resting on a WEAK premise is weakened, not strengthened, by a stronger premise you did not check - and the unnecessary sentence is the one that reads as rigorous.

The lesson

When an argument is already sound on a premise that is trivially true, adding a stronger-sounding premise that has not been measured does not make it more convincing - it inserts the only falsifiable claim in the whole argument, and puts it in the sentence a reader is least likely to challenge, because it is the one that sounds like it came from evidence. The word to distrust in your own prose is ONLY: `the ONLY project`, `the ONLY join`, `the ONLY place`. It is a claim about an entire set, it is almost never what the argument needs, and it is nearly always cheaper to delete than to verify.

What happened

DW-080 phase A, 2026-08-28 (`DEF-113`), twice in one session. (a) Establishing which lines a CI coverage gate meant, the argument needed only that the local test set is a SUBSET of CI's - trivially true, and enough, since coverage is monotone in tests executed and equal counts then force set identity. Written up, it acquired *"`Acmp.Application.Tests` is the ONLY project whose tests reach this file"*, which was never measured and is false; `Acmp.Api.Tests` reaches it too. (b) An hour later the fix's write-up called `StopAsync` *"the only deterministic join"*. Also unmeasured, also false - it cancels the stopping token before awaiting - and CI rejected the fix built on it. Both sentences reached a pushed commit message, which cannot be amended. In (a) the conclusion survived untouched because the extra premise was load-bearing for nothing; in (b) it did not.

What to do instead

Before writing a durable artifact, identify the WEAKEST premise the argument actually needs and state that one. Then treat every remaining `only`, `never`, `always`, `cannot` and `the single` in your own draft as a measurement request: either run the command that settles it in the same breath, or strike the word. A sentence that can be deleted without weakening the conclusion should be deleted rather than verified - it is pure liability, since it can only ever be wrong.

Why it generalises

An unnecessary premise carries all of the risk and none of the load. It cannot strengthen a conclusion that already follows, but it can be false, and when it is, it discredits the surrounding reasoning that was in fact correct - or, worse, it is load-bearing for the NEXT decision, where nobody re-checks it because it arrived attached to an argument that was verified. Universal claims are the common form because they read as thoroughness, and thoroughness is exactly what a reader declines to re-derive.

If followed

Durable artifacts carry the premises their conclusions actually rest on, so a reader who checks one sentence checks the one that matters, and the register keeps its authority when a claim does turn out wrong.

If ignored

An unmeasured universal ships inside a verified argument, inherits its credibility, and is later reused as an established fact by a session that has no reason to doubt it - and it reaches commit messages, which cannot be amended.
