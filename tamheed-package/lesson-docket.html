WRITING CODE INTO A FILE THROUGH ANOTHER LANGUAGE SILENTLY EATS ITS ESCAPES, AND THE RESULT STILL LOOKS PLAUSIBLE - SO PROVE GENERATED CODE RUNS, NEVER READ IT AND BELIEVE IT

The lesson

When a script generates source for another file - a Python heredoc writing TypeScript, a shell heredoc writing a Dockerfile, any generator emitting code - every escape sequence passes through TWO levels of interpretation, and the outer one usually wins silently. `'\\n'` in a Python string becomes a real newline in the output file, not the two characters a JS or regex literal needs. The generated file then contains a string split across two lines, or a character class broken in half.

WHAT MAKES IT EXPENSIVE IS THAT THE DAMAGE LOOKS FINE. The output is still readable, still nearly right, and a `grep` for the surrounding text still matches. The failure surfaces later as a parse error in a test run, or - worse - as a snippet embedded in documentation that nobody executes until the session that needs it.

FOUR OCCURRENCES IN ONE SESSION, 2026-08-26, each costing a cycle. (1) A Dockerfile written for a forced-build test: `FROM alpine:3.20\\nRUN sleep 30` became two source lines and the C# would not compile. (2) A test fixture: multi-line document bodies became unterminated string literals, and the whole test FILE failed to load - reported as 59 passing tests and one failed file, which reads like a test failure and is not. (3) and (4) A regex embedded in a markdown code block, twice: the character class `[^.\\n]` split across two lines, producing a snippet that would have failed for whoever copied it.

THE ASYMMETRY WITH ORDINARY TYPOS. A typo in code you write directly fails at the point you wrote it. A mangled escape in code you GENERATE fails at the point someone else runs it, which may be a different session, and the generator that produced it has usually been thrown away by then.

What happened

WBS-24.2 / WBS-24.3 / DW-084, 2026-08-26. Found by hitting it four separate times in one session; the fourth was inside the pre-handoff pass whose whole purpose is catching things a fresh session would trip over - which is where it would have done the most damage, because the reader would have copied a broken snippet out of the resume.

A FIFTH OCCURRENCE, WBS-24.4, LATER THE SAME DAY - AND IT IS THE ONE THAT ARGUES HARDEST FOR THE RULE, because it happened to an agent who had just written this lesson down. A bash heredoc quoted `<<'EOF'`, the form believed to be literal, was used to write a Node scanner containing a path-separator regex. One backslash level was eaten anyway: the file arrived with the escape missing and Node refused to parse it. It cost only minutes BECAUSE the very next action happened to be running the generated script - the recommendation below, applied by accident rather than by discipline.

WHAT THE FIFTH ADDS THAT THE FIRST FOUR DID NOT. The first four are one shape: an outer language interpreting an escape meant for the inner one. The fifth shows that KNOWING THIS, AND HAVING JUST WRITTEN IT DOWN, DOES NOT PREVENT IT - and that the quoting form assumed safe was not. So the defence cannot be vigilance, or a remembered rule about which heredoc is literal; it has to be the mechanical one: run the thing. In this instance the better remedy was also simpler than the rule suggests - the file was rewritten with the editor tool instead of through a heredoc, REMOVING THE SECOND INTERPRETATION LAYER ENTIRELY rather than trying to escape correctly through it.

What to do instead

Build the escape explicitly rather than trusting it through a layer: `chr(92) + 'n'` in Python, or a placeholder token substituted afterwards. Then - and this is the part that actually catches it - PROVE THE GENERATED CODE RUNS. Extract the block and execute it, compile the file, or run the test that loads it, in the same breath as writing it. Reading the output and finding it plausible is exactly the check that fails here, because plausible is what the damage looks like. For a snippet embedded in prose, where nothing compiles it, extraction-and-execution is the ONLY check there is.

Why it generalises

Escape mangling is invisible to every instrument this project already trusts. A gate compiles committed source, not a heredoc's intent; an id-and-status pass reads identifiers, not string literals; and a snippet inside a markdown fence is not code to any tool in the repository. The generator is also usually a throwaway, so there is no artefact left to re-inspect when the breakage is noticed. The only moment the fault is cheap to catch is immediately after generation, and only by execution.

If followed

Generated code either runs or fails in the session that produced it, while the generator still exists and the intent is still in hand.

If ignored

Mangled escapes ship inside test fixtures, Dockerfiles and documentation snippets, and surface as parse errors or broken copy-paste in a later session that has no idea a generator was involved.
