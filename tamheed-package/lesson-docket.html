Before you read

An approved lesson is immutable. The store refuses an edit to one — a change means writing a new lesson that supersedes it. So approving is the expensive direction, and rejecting costs nothing but the row.

Approving is not the same as agreeing a finding happened. These sentences were written by the agent, not by you. Selecting a finding is not approving the wording it was written up in.

  • Approve and pin — binds every future session and is written into the note the agent loads at startup. Reserve it for the ones worth interrupting someone with.
  • Approve — binds, but stays out of the startup note.
  • Reject — the row stays as history and binds nothing.
  • Refine — tell me what is wrong with the sentence and I will rewrite it for another pass.

The lesson

A TEST WHOSE FIXTURE IS THE LIVE REGISTER IS A TEST WHOSE MEANING CHANGES WHEN SOMEBODY DOES ORDINARY WORK, AND THE DANGEROUS OUTCOME IS NOT THE FAILURE - IT IS THE PASS. If a test SELECTS its subject from mutable state rather than constructing it, then a promotion, a status flip or an added row can silently substitute a different subject; the mutation still applies, the code still runs, and the assertion is now about something that was never under test. It may still pass - for a reason that has nothing to do with what the test names.

What happened

A three-case regression suite was written for the slice-review slate generator (DEF-117, DEF-119) and committed. Its third case was a deliberate calibration: strip the recorded reason out of a criterion-less work item and assert the generator STILL refuses it. Each case copied the store to a scratch tree and set ONE row's lifecycle_status to Review, leaving every sibling as the live register happened to have it. Hours later, in the same session, the operator promoted that row to Implemented (DEC-092). The calibration's mutation still applied and the generator still ran - but on a DIFFERENT item, never under test, which carried a citation and therefore rendered. Filed as DEF-120.

What to do instead

Stage the whole SELECTION, never one row. Force the row under test into the state that selects it, force every sibling OUT of that state, and write the shape being tested into the row rather than inheriting it - so the case asserts a PROPERTY of the code under test rather than a fact about today's register. Then demand the cheap proof that the coupling is gone: the fixed test must pass under the exact live state that broke it. THE DISCRIMINATOR FOR SPOTTING IT BEFORE IT BITES: ask what a normal day's work would have to change for this test to stop testing what it names. If the answer is a status column, an added row, or a promotion - anything a colleague could do without touching the code under test - the fixture is coupled and the pass is not load-bearing.

Why it generalises

THE LOUD FAILURE WAS LUCK, AND THAT IS THE WHOLE LESSON. The surviving Review row happened to carry a DW- citation, so the generator exited 0 against an expected 2 and the breakage was visible. Had that row instead lacked citations - one title-edit away, and the ordinary state of an item early in its life - the generator would have exited 2 WITH THE EXPECTED MESSAGE FOR A COMPLETELY DIFFERENT REASON, and the calibration would have reported PASS while testing nothing, indefinitely. A calibration that can pass for the wrong reason is the hollow pass it exists to prevent. IT IS NOT SIMPLY 'MOCK YOUR DATA': reading real rows was the right call and is what makes the suite meaningful, since it exercises real shapes a fixture would not. The error was finer - the SUBJECT SELECTION came from live mutable state rather than being established by the test. The generator's input is 'the set of rows at Review in slice X', so a test of it must CONSTRUCT that set.

If followed

Regression suites over the Tamheed package keep meaning what they say as rows are promoted, added and re-statused in the ordinary course of work, and a calibration that stops discriminating fails loudly instead of going quietly green.

If ignored

A hollow pass in the regression suite for the instrument that discharges LL-011, which would eventually let an unrenderable work item reach an operator review as a hand-built page - the exact harm DEF-116 and DEF-117 were filed to prevent. More generally it is LL-015's fault (a true result about the wrong set) operating on a test fixture instead of on a scan scope, and LL-013's fault-injection cannot catch it, because the injection lands on a subject the test no longer examines.
