LL-029 Recreating a failure on demand feels like proof of its cause, and it is not. improve verification
LL-029 improve verification Proposed

A REPRODUCTION THAT CHANGES TWO THINGS AT ONCE CONFIRMS WHICHEVER ONE YOU WERE ALREADY LOOKING AT - AND IT IS THE STRONGEST-FEELING EVIDENCE THERE IS, BECAUSE YOU MADE THE SYMPTOM COME BACK ON DEMAND.

The lesson

Recreating a failure on demand feels like proof of its cause, and it is not. It is proof that SOMETHING in what you changed is sufficient to produce the symptom. If the step you took to set up the reproduction altered more than one thing, the reproduction cannot distinguish between them - and it will silently credit whichever one you were already watching, because that is the one you wrote down as the precondition.

THE ASYMMETRY THAT MAKES THIS DANGEROUS: a reproduction CONFIRMS, only an intervention EXPLAINS. Confirmation is cheap, satisfying, and available for every wrong hypothesis that happens to travel with a right one. The test that actually separates causes is to change ONE variable and predict the outcome BEFORE running it - and the most informative version of that is the fix, because a fix that fails under the true precondition falsifies the mechanism you built it on.

What happened

`DEF-114`, 2026-08-28. `DW-085`'s forced-build guard failed locally and passed in CI. Hypothesis: Testcontainers skips a build when the named image already exists. To confirm it I pre-created the image and re-ran the single test; it failed identically in 804 ms. That was recorded as *"PROVEN by reproduction"* and written into the defect row, a progress entry, the resume, the memory index and THREE pushed commit messages, alongside an explicit statement that the rival explanation - Docker's layer cache - had been *"measured and DISCARDED"*.

**Pre-creating the image did two things: it created the named image, AND it warmed the `RUN sleep 30` layer in the build cache.** The cache was the real cause. The rival explanation had been dismissed on a 33-second identical rebuild measured minutes after the daemon started, with the cache cold - a true number about a state that no longer held. Warm, and under a brand-new tag, the same build takes about two seconds.

IT WAS CAUGHT ONLY BECAUSE THE FIX FAILED. A per-run image TAG was applied, the test was re-run against the true precondition, and it still failed - which no amount of further reproduction would ever have revealed, because the reproduction kept working perfectly.

What to do instead

1. Before recording a mechanism, list everything your setup step changed - not everything you INTENDED it to change. Creating a file, pulling an image, running a build and starting a daemon all have side effects that are part of your experiment whether or not you named them. 2. Isolate: vary ONE thing and predict the result before running it. Two conditions that always travel together are one condition until you separate them (`LL-009`'s independence test, applied to preconditions rather than to instruments). 3. Treat the FIX as the real experiment - apply it against the true failing precondition and require the symptom to disappear. A fix that fails there falsifies the mechanism, and that is the cheapest falsification available. 4. When a measurement is used to RULE OUT a rival explanation, record the ambient state it was taken in; a number that eliminates a hypothesis deserves more scrutiny than one that supports it, because eliminating closes off the search.

Why it generalises

A reproduction is an existence proof over a conjunction: it shows that the set of things you changed is jointly sufficient. Attributing the effect to one member of that set is an inference the reproduction does not license, and nothing about the experience of watching the failure return distinguishes the two. The feeling of rigour scales with how reliably the symptom returns, which is exactly the wrong signal - a confounded setup reproduces just as reliably as an isolated one, often more so, because it changes more.

If followed

A recorded mechanism is one that survived an attempt to separate it from its neighbours, so the fix built on it works the first time and the register stops carrying confident causes that were never isolated.

If ignored

A wrong cause ships with the full rhetoric of proof - 'reproduced', 'measured', 'discarded' - into rows, prompts, memory and commit messages that cannot be amended, and the fix built on it fails while the diagnosis it rests on keeps being cited.
