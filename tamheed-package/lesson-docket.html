LL-030 improve verification Proposed

A defence-in-depth layer can be structurally invisible to every test that enters through the front door

The lesson

A DEFENCE-IN-DEPTH LAYER CAN BE STRUCTURALLY INVISIBLE TO EVERY TEST THAT ENTERS THROUGH THE FRONT DOOR, AND THE MORE LAYERS YOU ADD THE MORE OF THEM BECOME UNTESTABLE THAT WAY. A layer's correctness is only observable through a request that REACHES it, so whenever an EARLIER layer refuses the entire population that a LATER layer exists to refuse, the later layer's rule cannot be exercised from outside at all. That is not a gap in the tests; it is a property of the composition, and it gets WORSE as protection improves, because each new outer layer shadows more of the inner ones. The shadowed layers are exactly the ones a future refactor can weaken with no test noticing.

What happened

WBS-24.8 guards a targeting parameter with three independent layers: an SPA route guard, a path gate that refuses guest-only principals, and a role set on the query itself. The source asserted that adding Guest to that role set was 'the single mutation' that would let a guest read somebody else's slot. Written rather than measured, and FALSE: the path gate intercepts every guest before any handler runs, so the mutation can be applied and ALL TEN of the surface's HTTP tests stay green. Demonstrated by applying it rather than by argument.

What to do instead

Two parts. FIRST, for each layer ask which population it UNIQUELY refuses; where the answer is 'none, from outside', assert that layer at its own boundary instead - here, against the authorization pipeline directly, with no HTTP and no middleware. SECOND, give each layer a DISTINGUISHABLE SIGNATURE and assert on the signature rather than on the status code: a path gate that sets a refusal-reason header and an application-layer refusal that emits an audit row can be told apart, whereas three tests all asserting 403 read as rigour while testing whichever layer happens to run first, and would keep passing if any one of them were deleted. And treat every 'the single X', 'the only way' or 'cannot' written about a control as a request to run the mutation - that is LL-028 applied to a security claim rather than a measurement.

If followed

Each layer is proven independently and by its own evidence, so the composition can be rearranged later without silently losing a control; and the false-confidence sentence gets caught while it is still a draft.

If ignored

A weakened inner layer ships silently. The tests that appear to cover it are covering an outer layer, so removing or narrowing the inner rule changes nothing visible until the outer layer is itself moved or relaxed - at which point the exposure is immediate and nothing in the suite ever flagged it.

LL-031 improve verification Proposed

A refactor can push a file under a per-file coverage floor without adding one untested line

The lesson

A REFACTOR CAN PUSH A FILE UNDER A PER-FILE COVERAGE FLOOR WITHOUT INTRODUCING A SINGLE NEW UNTESTED LINE, BECAUSE THE FLOOR IS A RATIO AND A REFACTOR MOVES THE DENOMINATOR. The inverse is equally invisible and matters more: ADDING covered code to a file raises its percentage and can carry pre-existing untested lines back over the threshold, so a file can silently STOP reporting a real gap because unrelated well-tested code landed beside it. A per-file ratio does not measure what is untested; it measures what is untested RELATIVE TO what is tested in the same file, and both halves move for reasons that have nothing to do with either.

What happened

Extracting a shared composer moved about thirty-six lines of COVERED composition out of one handler, taking it from 191 source lines to roughly 155. Three early-return guards in that file had never been executed by any test and still were not; nothing about them changed. Their share of a smaller file crossed the five per cent budget and CI failed the file - which reads unambiguously as 'the code you just added is untested' and sends the next reader to inspect new code they will find fully covered.

What to do instead

When a per-file floor fails after a refactor, diff the UNCOVERED LINE NUMBERS against the previous run before diagnosing anything - not the percentage, and not the file. If the set is unchanged, the refactor EXPOSED a pre-existing gap rather than creating one, and the record should say so. The gap is still worth closing; what is wrong is the story about where it came from.

If followed

The diagnosis matches the cause, the commit message and the verdict attribute the gap honestly, and the pre-existing guards get forced instead of being carried further.

If ignored

Two failures. Time is spent auditing correctly-covered new code while the real gap sits in untouched guards; and in the opposite direction a genuine gap disappears from the report when unrelated covered code is added, so the floor stops reporting something it never stopped being true about.
