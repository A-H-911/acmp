The lesson

TRAP 13 SAYS *build payloads from `data/*.jsonl`, never from `entity_query` output, because the store holds truncated rows* — and it names the STORE as the source of short text. THE TRUNCATION CAN JUST AS EASILY BE ON YOUR OWN SIDE OF THE PIPE. A field read from the canonical JSONL for the purpose of LOOKING at it, printed with a `[:400]` slice for readability, is exactly as dangerous as a truncated store read, and the guard *use the JSONL* does not fire on it because the JSONL genuinely was the source.

THE GENERAL FORM IS WIDER THAN THE TRAP AS WRITTEN: A FIELD IS SAFE TO RE-TRANSMIT ONLY IF IT CAME FROM A READ WHOSE PURPOSE WAS TRANSMISSION. Any text that has passed through a display — a terminal print, a summary line, a table, a preview, an excerpt — is suspect regardless of where it originally came from.

AND THE SECOND HALF IS WHAT MAKES A LENGTH HEURISTIC USELESS: TRANSCRIPTION FIDELITY DOES NOT DEGRADE WITH LENGTH IN THE WAY INTUITION PREDICTS. In one session a 9386-character field was re-transmitted byte-perfectly and a 2959-character field — shorter, and authored minutes earlier — came back with a silent word inserted. **So size cannot be used to decide which writes deserve a check. Every re-transmitted field gets the same hash-and-verify, or the practice is a coin flip dressed as a policy.**

What happened

2026-09-01. Amending `DW-071` required a full row because `deferred_work.title` is NOT NULL. The payload's title was composed from a line of the session's OWN earlier sweep output, which had printed `title[:400]` for terminal readability. The upsert returned `ok` and destroyed 1697 of 2097 characters — every sentence after the first paragraph, including the whole coverage-gap argument and the row's explanation of why it was a deferred-work row rather than an acceptance criterion. In the same session, `SC-044`'s 2959-character description drifted by one inserted word while `WBS-26.4`'s 9386-character title, `DW-091`'s 6079 and `WBS-26.5`'s 6775 all went byte-perfect.

What to do instead

Re-transmit a NOT NULL field only from a read taken FOR that transmission — emit it as a JSON literal from the canonical file and paste that, never a value that has been through a print, a summary or an excerpt. Hash the field BEFORE the write, compare after, and CALIBRATE the comparison by injecting a one-character corruption first (`LL-013`) — an equality check that has not been shown to discriminate proves nothing. Apply it to every field regardless of size, because size does not predict which one will drift. Where a row genuinely changed, prefer appending to it over re-typing it to preserve it, so the verification is a clean prefix check.

Why it generalises

The failure is invisible to everything the package owns. `gate_run()` returns 7/7 over a 400-character title; `G-IDS` checks foreign keys and the entity index, not field lengths; `readiness_check` never reads the field; and no gate is column-level — the v2.3 migration already established that every gate is row-level, which is why it passed 7/7 while damaging register data. A truncated row simply stays truncated, and the loss is discoverable only by someone who happens to remember what used to be there. The pre-image that caught this existed only because hash-and-verify had been adopted earlier in the same session against a DIFFERENT hazard, so the catch was luck riding on an unrelated habit.

If followed

A silent field truncation becomes a loud, immediate failure with a byte-exact restore path, and the check is applied uniformly instead of by a size intuition that this instance disproved.

If ignored

Authoritative register rows lose most of their content on a write that reports success, with no gate, readiness rule or view able to report it — and the loss surfaces only if a human recalls the missing text.

LL-046 improve verification Proposed

A PRESCRIBED instrument can go stale against the artifact it measures, and it then returns a confident WRONG number rather than an error — so a documented command is a claim to re-verify, not an authority to quote.

The lesson

`LL-033` warns that a pattern matching a spelling the corpus does not use hands back a confident wrong subject. THE SHARPER CASE IS WHEN THAT PATTERN IS THE ONE YOUR OWN DOCUMENTATION TELLS YOU TO RUN. A committed instruction to *measure it with this command* carries the authority of having been written deliberately, by someone who had checked — and it keeps that authority long after the artifact it measures has been rewritten underneath it.

THE FAILURE IS NOT THAT THE COMMAND ERRORS. It runs, it has a subject, it returns a plausible number, and the number is wrong. A prescribed grep for literal `page.goto('/x')` calls returned FIVE routes for an accessibility sweep that visits TWENTY-THREE, because the sweep had been rewritten to iterate a `ROUTES` array through a helper — a change that made the sweep four times wider and the prescribed instrument blind at the same moment.

**AN INSTRUMENT AND THE ARTIFACT IT MEASURES ARE ONE DECISION IN TWO PLACES, AND ONLY ONE OF THEM IS EXERCISED BY CI** — `LL-019`'s shape, moved from a pinned base image and its package repo onto a measurement and its subject. **What catches it is refusing a number that disagrees with something you independently know**, not re-reading the command.

What happened

2026-09-01. `prm-next.md` carries the instruction *"DO NOT RE-QUOTE A COVERAGE RATIO FROM HERE; MEASURE IT"* followed by the exact command — a grep for `page.goto('…')` over `rtl-a11y.spec.ts`. Run as prescribed while measuring `DW-071`'s stale figure for an operator interview, it returned 5. PR `#336` had days earlier replaced the enumerated visits with a `SECRETARY_ROUTES` constant iterated by a `violationsByRoute` helper, adding 18 routes the literal pattern cannot see. The true figure is 23 distinct static routes. The wrong number was caught only because it contradicted a known event — `#336` was recorded as having swept 18 routes, which 5 cannot accommodate.

What to do instead

Treat a documented measurement command as a claim with a date on it, not as an authority. Before quoting its output into anything durable, check it against something you know independently — a recorded event, a control term, a second key on a different property (`LL-009`: two instruments agreeing is one instrument when they share a mechanism). When an instrument and its subject can drift apart, say so where the instrument is written down, and prefer a pattern keyed on the artifact's STRUCTURE over one keyed on a spelling. Where a number will be put in front of the operator, state the instrument beside it so they can disagree with the instrument rather than with the figure (`PE-613`).

Why it generalises

The prescription exists precisely because a stale COUNT was dangerous, so it was replaced with a command — the standing remedy of giving the command rather than the answer. But that remedy silently assumes the command is stable while only the answer moves. Here the command rotted and the answer it produced was worse than a stale figure would have been, because it arrived wearing the authority of a live measurement taken exactly as instructed. The instrument's own documentation cannot warn about this: it was correct when written, and nothing compares a documented pattern against the file it targets.

If followed

A documented measurement is re-verified against an independent fact before it enters a decision, so a rotted instrument is caught at the moment it would otherwise have been most persuasive.

If ignored

A wrong number reaches an operator interview or a durable record carrying the authority of the project's own prescribed method, and the disclaimer *measure it, do not quote it* actively vouches for it.
