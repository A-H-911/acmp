OPERATOR DECISION, 2026-08-29, ON `DW-080` PHASE B AFTER THE SPIKE: d1 THE BASE IS `aspnet:10.0-noble-chiseled-extra`. d2 THE HEALTHCHECK BECOMES A TINY .NET PROBE INVOKED WITHOUT A SHELL. Decision, as stored

d1 - THE api AND worker IMAGES MOVE TO `mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled-extra`. Measured against the four alternatives: 162 MB against Debian's 229 (-29%); medium CVEs 26 -> 4 and low 13 -> 7, with NO highs, where BOTH alpine variants carry two highs that neither Debian nor chiseled has; glibc rather than musl, which removes the native-interop risk `DW-066` and `DW-080` both name around `Microsoft.Data.SqlClient`; and ICU 74.2, the SAME version Debian ships, which is why the same published binary produced BYTE-IDENTICAL Arabic output on both. It satisfies `NFR-054`'s 'equivalent distroless' clause, which `SC-024` kept rather than relaxed.

REJECTED: `10.0-alpine-extra`, and the reason is the finding the spike exists to have produced. It is 3 MB smaller and keeps a shell, so the healthcheck would have survived untouched - but it ships ICU 78.1 against Debian's 74.2, and CLDR changed `ar-SA`'s default calendar in that range, so the SAME binary renders a Hijri date on Debian and a Gregorian one on alpine-extra. No exception, no log line, Arabic only. It also carries the two high-severity CVEs and reintroduces musl. The convenience was real; the two costs are precisely the ones this project weighs heaviest.

ALSO REJECTED: plain `chiseled` or `alpine` with no ICU, despite being smallest and cleanest on CVEs. They are defensible ONLY on the measured fact that ACMP's API does no culture-aware work today, and they do not fail loudly if that ever changes. ALSO REJECTED: staying on Debian, which would leave `NFR-054`'s clause unsatisfied and reverse `SC-024`.

d2 - THE api HEALTHCHECK BECOMES A SMALL .NET PROBE INVOKED AS `CMD` WITH NO SHELL. Chiseled ships no shell and no package manager, and the current check is `CMD-SHELL` running `curl -f http://localhost:8080/readyz`, so it cannot survive the base change in any form. The probe is published beside the application and invoked through the `dotnet` host already present in the image, and it keeps probing `/readyz` exactly as today.

WHY NOT THE CHEAPER ROUTES, recorded because the cheapest one is the trap. Copying a static `curl` in would be the smallest diff and zero new code, but it puts a native binary back into an image whose entire purpose is minimal surface, and it then needs tracking and patching like any other dependency. Moving the check to the compose layer as a TCP probe needs nothing at all - and rebuilds `DEF-079` exactly, where a healthcheck that could only fail if the process stopped answering TCP was itself the defect, on a `/healthz` endpoint mapped with a predicate that evaluated NO checks. `/readyz` reaches SQL Server, Hangfire and object storage, and that reach is the whole value of the check.

Rationale, as stored

THE SPIKE FALSIFIED THREE CLAIMS THE PACKAGE ITSELF CARRIED, and the decision rests on the corrected picture rather than the recorded one.

FIRST, and it inverts the risk. `prm-next.md` and `DW-080` both said a naive minimal-base move would not degrade Arabic but would THROW at runtime after compiling and unit-testing perfectly. Measured by publishing ONE binary and running it unchanged on all five bases: a no-ICU image does NOT abort at startup. The app starts, exits 0, and silently enters globalization-invariant mode, throwing only when a non-invariant culture is TOUCHED. And ACMP's API touches none - all 10 `CultureInfo` usages in `src` are `InvariantCulture`, and `RequestLocalization`, `SupportedCultures`, `IStringLocalizer`, `Accept-Language`, `new CultureInfo` and `.resx` return ZERO across 693 `.cs` files. So the predicted loud failure would not have happened; what would have shipped is a container in which the first server-side culture-aware code anyone ever writes throws in Arabic, with nothing failing in between. The trap is armed and invisible rather than loud, which is worse than the row predicted, not better.

SECOND, the risk was framed as musl versus glibc and the risk that actually bites is the ICU VERSION, which is orthogonal to it and would have applied to a glibc option too.

THIRD, `DEC-083` d2 asked what a no-ICU base implies for `FREETEXT` and `LCID 1025`. Measured: nothing. Every `LCID 1025` reference is an EF migration creating a full-text index with `LANGUAGE 1025`, executed inside the `sqlserver-fts` container - an image `NFR-054` excludes from the size cap and this change does not touch at all. Arabic word-breaking cannot be affected by the api base, and the spike's attention went to the culture surface that CAN be.

AN INSTRUMENT FAILURE IS RECORDED BECAUSE IT NEARLY DECIDED THIS WRONGLY. The probe printed 'invariant-mode: off' on the very images where the runtime WAS in invariant mode: `AppContext.TryGetSwitch` reports the explicit SWITCH, and the runtime falls back to invariant when ICU is absent WITHOUT setting it. Reading the flag would have reported every base as healthy. The behavioural probe - attempt a culture and see what happens - is what produced the true answer. Separately, a PowerShell tar probe reported NO ICU for `chiseled-extra` whose own behaviour proved otherwise; the bash form measured ICU 74.2, and nothing was reported until the two agreed, because a verifier that disagrees with observed behaviour is the verifier being wrong.
