Criterion, as stored

For EACH of C-INS-01's two anomaly signals, the application detects the condition and emits a distinct, queryable audit event, and each signal is proven per signal rather than in aggregate:

**Signal 1 - atypical bulk-export volume.** An audit-log export whose delivered row count reaches the configured threshold emits an `Audit.BulkExportAnomaly` **AuditEvent ROW**, IN ADDITION TO the C-AUDIT-08 `audit.exported` record and never in place of it. An export below the threshold emits the ordinary record and NO anomaly row.

**Signal 2 - atypical `Restricted`-topic access.** A successful read of a `Restricted` topic emits a `Topics.RestrictedTopicAccessed` **AuditEvent ROW** - which did not exist before this item and without which the signal was undetectable by any mechanism. When one principal's accesses within the configured window reach the threshold, a distinct `Topics.RestrictedAccessAnomaly` row is emitted. A single read emits the access row and NO anomaly row.

**The threshold basis.** Every threshold is recorded as **provisional pending a baseline** (`DEC-099` d3) and its value is held in the `ConfigurationSetting` store rather than in code, so it can be replaced from observed usage without a deployment.

⚠ **THE RECORDING IS PLACED AFTER THE VISIBILITY CHECK, AND THAT IS PART OF THE CRITERION.** A read the caller was not permitted must leave NO access row: above that line the refusal is deliberately indistinguishable from *no such topic*, so recording there would both log reads that never happened and leak, into the audit log, the existence of topics the classification exists to hide.

⛔ **WHAT THIS CRITERION DOES NOT COVER.** The Seq alert RULE that notifies on these events - `DEC-099` d2 puts detection in the application and notification in Seq, and the Seq half belongs to the ops/runtime group. C-INS-01's *optional dual-control* clause, which stays with `OQ-025` (`Deferred`).
