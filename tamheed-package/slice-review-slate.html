What follows is what the row bought.

THE ROW'S CENSUS WAS RIGHT AND ITS PRESCRIPTION WAS NOT. It said the work was 'extracting one shared hook and routing rendered numbers through it, not designing anything'. The census held exactly - two `Intl.NumberFormat` call sites in 347 files - but a hook reaches only ONE of the two ways a number gets onto a screen. The other is a value handed to `t()`, ~50 of them, which no per-site hook can cover and which no future author would remember.

WHAT WAS BUILT INSTEAD, and the shape matters more than the diff. The `t()` path is closed CENTRALLY by a formatter MODULE on the i18n instance, keyed on the RUNTIME TYPE: a number is localized, while an entity key, an ADR identifier and a pre-formatted date - all strings - pass through untouched. Zero call sites and zero locale-file entries were edited, and a numeric placeholder written after this date is covered automatically. The bare-JSX path became 37 `<Num>`/`<Pct>`/`<Bytes>` instances across 19 files.

⚠⚠ THE OBVIOUS WIRING IS A SILENT NO-OP, AND THIS IS THE DURABLE FINDING. `interpolation.format` reads like the hook and is not: i18next OVERWRITES it with its own Formatter during init, and that Formatter returns the value untouched when no format is named (`if (!format) return value`). A formatter module plus `alwaysFormat` is what actually fires. Both halves are mutation-proven; removing either turns three tests red and leaves every number silently Latin.

THREE BYPASSES THE CENTRAL FIX STRUCTURALLY CANNOT SEE, all closed: `jobFormat.formatDuration` returned `String(ms)`/`toFixed(1)` and now returns a number; `WikiReadingView` pre-formatted its read time before handing it to `t()`; and `Intl.RelativeTimeFormat` needed the same `ar-u-nu-arab` pin because it emits digits too. ⚠ A VALUE PRE-STRINGIFIED BY ITS PRODUCER IS INVISIBLE TO A TYPE-KEYED FORMATTER - that is the class, and it will recur.

THE ROW'S SECOND NOTE WAS ALSO ACTED ON: three separate byte formatters existed, two of them Latin-only. One shared `formatBytes` replaces them. They DISAGREED on rounding, so merging had to choose - the mockups draw '25 MB' and '1.2 MB' (INV-014), i.e. `maximumFractionDigits`, not `toFixed`, which changed SubmitTopic's '3.0 MB' to '3 MB'.

⭐ AN INV-014 MISS THE FIRST COMMIT SHIPPED, found only by checking the design references over a question nearly waved through: the mockups draw `٤٠٪` with U+066A, the ARABIC percent sign, and the app was gluing an ASCII `%` onto the digits - so the first commit produced `٨٧%`. THE SIGN IS PART OF THE NUMBER FORMAT, NOT A SUFFIX; `style: 'percent'` makes Intl choose it per locale.

⚠ WHAT IS DELIBERATELY NOT LOCALIZED, each stated where it lives: the CSV export in `reportViews.viewToCsv` (a spreadsheet is its reader, not a person), the audit trail's clock (en-GB with `numberingSystem: latn`, by design), and entity identifiers. A number reaching an ATTRIBUTE rather than a text node was not swept.
