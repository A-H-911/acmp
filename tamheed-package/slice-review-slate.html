The requirement — FR-164

As stored

As a Secretary or Chairman, I want to correct a topic's type and source while it is still in triage, so that a topic submitted under the wrong classification can be fixed in place rather than rejected and resubmitted. The correction shall be available only before Acceptance (Draft, Submitted, Triage or Reopened) and shall be refused once the topic has been accepted, because classification drives the required template, the triage workflow and the SLA thresholds that acceptance has already applied. It shall be restricted to Chairman and Secretary - not the topic's owner or submitter - so that classification remains a triage judgement rather than self-service. A correction that changes nothing shall be a no-op. Every correction that does change something shall be recorded in the audit trail with its before and after values; no status transition is written and no reason is required, so the audit record is the only place the previous classification survives.

The deferred-work row it closed — DW-076

As stored

TopicSource IS A NINE-VALUE DOMAIN VOCABULARY THAT NO SURFACE IN THE PRODUCT HAS EVER SHOWN OR OFFERED, AND IT HAS NO BILINGUAL LABELS AT ALL. Found 2026-08-21 while building WBS-23.4, which needed to decide whether the reclassify dialog should offer a source picker beside the type picker. THE FACTS, checked rather than assumed: `TopicSource` declares nine values (CommitteeMember, StreamRequest, UrgentOrgNeed, OperationalIncident, SecurityFinding, Modernization, InnovationInitiative, CrossStreamProblem, Regulatory). `SubmitTopic.tsx` sends a hardcoded `SOURCE_DEFAULT` and its own header records that as a P5a decision - the submitter never chooses one. A search of both locale bundles for any of the nine names returns ZERO keys; the only hit anywhere is `audit.entity.CommitteeMember`, which is a different vocabulary that happens to share a word. So every topic in the product carries a source, the domain and the API both take it, and no human has ever seen or set one.

WHY WBS-23.4 DID NOT ADD THE PICKER, so this is not read as an oversight. Exposing source means authoring EIGHTEEN new strings - nine English and nine Arabic - for governance concepts, and the Arabic half is the problem: NFR-039 requires a single canonical source of bilingual terms, LL-010 records that the glossary it names is a circular pointer between two English documents and does not exist, and DW-069 carries building it. Inventing nine Arabic governance terms inside a feature slice is exactly what that requirement forbids, and it would seed terminology the glossary would later have to either bless or contradict. The reclassify endpoint therefore takes BOTH fields, because the domain method does and the API is the contract; the SPA sends the topic's existing source back unchanged.

WHAT IS ACTUALLY BLOCKED AND WHAT IS NOT. The API is NOT blocked - a caller can already correct a source today through POST /api/topics/{id}/reclassify, and AC-143 says so while deliberately not claiming a UI for it. What is blocked is the UI, and only on the terminology.
