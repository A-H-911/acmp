title: ADR-0047: Test consumers pull the SQL Server FTS image from a private GHCR package at a committed digest that tracks `Dockerfile.sqlserver` by hash; production's ECR path is unchanged. Supersedes ADR-0046 on approval, rewriting only d1's parity sentence.
context: `DEF-161`, `DEF-158` and `DEF-157` are one exposure: every test consumer builds the 4 GB FTS image from `deploy/Dockerfile.sqlserver` on every run, so each run samples a slow Ubuntu mirror, a context upload, or an apt repository against a fixed budget. `#402` cut the integration fixture to one build per run; `main`'s own run on that merge still failed on a single cold build stalled in `apt-get update` (`DEF-161`). `DEC-180` i6 chose the route (a pre-built image pulled at a pinned digest) and `DEC-182` its shape. Production already receives a pre-built image, pushed to ECR from `main` only, and PR runs cannot reach ECR by design (`deploy/aws/06-github-oidc.sh`: the role trusts exactly a push to `main`). The Dockerfile's apt layer installs whatever 2022 CU packages.microsoft.com serves on build day, so two builds of the same file on different days can differ in CU. `ADR-0046` d1 states that test and production *keep building the ONE file, so parity is preserved by construction*, and that sentence stops being true in its original sense once tests stop building.
decision: e1 - **TEST CONSUMERS PULL, FROM A PRIVATE GHCR PACKAGE.** The integration fixture, the e2e compose stack, and the shipped-image arm of the sampling harness pull the FTS image from a private GHCR package, `ghcr.io/a-h-911/acmp-sqlserver-fts-private`, which the operator created private from their own machine and granted to this repository (`DEC-183` g3); a dispatch-only workflow publishes into it and consumers pull it with `GITHUB_TOKEN`. No cloud credential is added. The package is never CREATED by a workflow: a workflow-published package *"inherits the visibility and permissions model of the repository where the workflow is run"*, and this repository is public (`DEF-163`).

e2 - **THE PIN IS COMMITTED AND TRACKS THE FILE BY HASH.** A repo file records the image digest together with the sha256 of the `Dockerfile.sqlserver` it was built from. A CI check fails when the file's hash differs from the pin. A consumer pulls only on a match. A candidate (`integration-on-candidate.yml`, a branch candidate in the sampling harness) is built, under an explicit switch, never pulled. A pull failure is a red, never a silent fallback to building.

e3 - **PARITY, RESTATED (REPLACES `ADR-0046` d1's SENTENCE).** Test and production are built from the ONE file. The test image is that file as of its last publish, and e2's check guarantees the file has not changed since. Production's ECR image is rebuilt on every merge to `main`, so the two can carry DIFFERENT 2022 CUs of the same file. That gap is accepted and bounded by the refresh in e4; parity is of the FILE, not of the binary.

e4 - **EACH CU BUMP COSTS ONE HUMAN STEP.** `ADR-0046` d2's allowed Dependabot digest bumps change the file and trip e2's check; for each, the publish workflow is dispatched on the Dependabot branch and the new pin committed there (`DEC-131` d2's shape).

e5 - **PRODUCTION IS UNCHANGED.** `ci.yml`'s ECR `publish` job, `docker-compose.cloud.yml` and `docker-compose.prod.yml` keep `ADR-0046`'s path.

e6 - **CARRIED FROM `ADR-0046`, BYTE-IDENTICAL, AT APPROVAL.** Before this ADR is put for approval, its decision gains `ADR-0046`'s d1 (with only its parity sentence replaced by e3) and d2-d5 verbatim, copied and verified by script against the store; on approval `ADR-0046` becomes `Superseded` with `superseded_by` this row.
