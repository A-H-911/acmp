LL-038 [lessons]

id: LL-038
title: A lifecycle status can be LOAD-BEARING rather than lagging, and the reason may live only in a progress entry no register view surfaces
statement: BEFORE 'REPAIRING' A ROW WHOSE STATUS LOOKS BEHIND ITS EVIDENCE, ASK WHETHER THE STATUS IS DOING WORK. A store constraint keyed on status - here, immutability that fires on `Approved` and not on `Proposed` - makes the un-promoted state the ENABLER of something, and promoting it is then not a tidy-up but a demolition. **The tell is UNIFORMITY: six of six rows in one slice is a decision; two of six is an oversight.** And the reason will not be in any register view - not in a status query, not in a readiness rule, not in a gate - because the thing that records a deliberate exploitation of a constraint is prose. **Sweep progress entries, not only decisions and ADRs: a progress entry is a ruling's record too.**
context: AC-088..AC-093 sat at `Proposed` with `Met` latest verdicts while 135 of 157 acceptance criteria were `Approved`, in a slice (SL-028) that was itself `Implemented`. The agent measured the shape, checked LL-006's trap by asking whether any DECISION or ADR had ever named the rows - three of the six were named by none - and concluded 'not previously ruled'. The operator ruled investigate-before-touching. PE-375 then gave the cause in terms: SL-028 was created RETROACTIVELY because FR-156 carried no implements edge, and the six criteria 'were bound to it directly - free, because the immutability trigger does not fire on Proposed'. Their un-promoted status is what made the binding possible. Promoting them would have made six deliberately-mutable criteria immutable, one-way, and would have destroyed the property the binding programme depended on.
recommendation: When a status looks stale against its evidence, run three checks before touching it. (1) Is it UNIFORM across a natural group? Uniformity is the signature of a decision. (2) Does any store constraint key on that status - immutability, a CHECK, a trigger, a foreign-key rule? If so the status may be load-bearing. (3) Sweep PROGRESS ENTRIES for the row's identifier, not just decisions and ADRs - LL-006's 'read the thing itself' extends to reading the thing that explains it, and that is often prose in an append-only log. Only then decide, and weight the decision by reversibility: an irreversible promotion made on an unmeasured cause cannot be undone.
rationale: It is LL-006's family - read the thing itself, not a proxy - with two additions that are not in LL-006. First, the thing to read may not be the ROW: every register view agreed with itself here and all of them were silent on the reason. Second, it supplies a positive TELL rather than only a warning: uniformity across a group distinguishes a decision from an oversight cheaply, before any deeper reading. It is also the reversibility half of DEC-101 d1's standard - that ruling said isolate a mechanism before writing a fix; this says the bar rises further when the action cannot be undone.

LL-039 [lessons]

id: LL-039
title: A GitHub Actions job reported `skipped` conflates two unrelated causes - the `if:` was false, and a job in `needs:` did not succeed - and the API prints the same word for both
statement: `skipped` IS NOT A REASON, IT IS AN OUTCOME WITH AT LEAST TWO CAUSES, AND THE ONE YOU CAN SEE IN THE WORKFLOW FILE IS THE ONE YOU WILL PICK. A job with both an `if:` condition and a `needs:` list reports `skipped` when the condition evaluates false AND when any needed job did not succeed. Reading the `if:` expression, seeing `skipped`, and concluding the condition was false is a match that fits and is not evidence. **The discriminator costs one query: read the conclusions of the jobs it NEEDS, or find a run where they passed.** More generally: when a status has several possible causes and only one of them is visible in the artifact you happen to be reading, you have not measured the cause - you have matched it.
context: Sizing WBS-26.3 I recorded that ci.yml's publish job 'is gated on github.event_name == push && github.ref == refs/heads/main && vars.AWS_ROLE_ARN != \'\', and it reported skipped on the #331 merge run, SO THE VARIABLE IS UNSET.' The observation was true; the cause was invented. Measured later, with a control: gh variable list returns AWS_ROLE_ARN set on 2026-08-04, three weeks earlier, and publish has needs: [backend, frontend, compose]. On the run in question backend FAILED, so publish was a dependency casualty. On the very next main run backend succeeded and publish=success. The if: gate had been satisfiable throughout. The needs: line sat ONE LINE ABOVE the if: in the same file and I did not read it.
recommendation: Never report why a job was skipped from the workflow file alone. Check both causes: (1) the conclusions of every job in its `needs:` on that same run, and (2) whether the `if:` expression's inputs are actually unset - for repository variables that is `gh variable list`, which is one command. Best of all, find a CONTROL run where the needed jobs passed: if the job ran there, the `if:` was never the blocker. And when writing the finding down, record what you MEASURED (`publish reported skipped on run N`) separately from what you INFERRED (`therefore the variable is unset`), so a later reader can see which half to distrust.
rationale: It is LL-020's family - a conclusion built on a misread does not travel with the correction - caught one step earlier, at the moment the conclusion is formed rather than after it has propagated. It is also LL-006's 'read the thing itself' with a specific target: the thing to read was the `needs:` line, not the `if:` line, and both were in the same file within one line of each other.
