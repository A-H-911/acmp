LL-047 [lessons]

id: LL-047
title: Choose the instrument by asking what a NEGATIVE result would mean — an instrument that cannot distinguish 'the hypothesis is wrong' from 'I cannot see it' turns every refutation into a coin flip you will read as a refutation.
statement: `LL-013` says prove the scanner looked at something before trusting a clean scan. THE PRIOR QUESTION IS WHETHER THE INSTRUMENT COULD HAVE PRODUCED A MEANINGFUL NEGATIVE AT ALL. `PE-769` measured a suspected memory leak by sampling the process WORKING SET on a 64 GB developer machine. On a box that never pressures the GC, working set is equally consistent with a leak and with ordinary lazy collection — so the baseline curve proved nothing, and, far worse, the intervention's UNCHANGED curve was equally consistent with 'the stores are not the cause' and with 'this instrument cannot see the difference'. The register was one step from carrying a confident REFUTED that the instrument had no power to support. The fix is one line — force a full collection and read retained MANAGED bytes (`GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect(); GC.GetTotalMemory(true)`), keeping working set as a secondary column — and with it the same experiment refuted the store hypothesis at 345 MB vs 335 MB and confirmed the real one at 137 MB vs 8 MB. SAME EXPERIMENT, SAME MACHINE, SAME AFTERNOON; ONLY THE INSTRUMENT CHANGED.
context: 2026-09-02, `DEF-109` third investigation pass (`PE-771`). `PE-769` had run the right experiment with an instrument that could not grade it, and had honestly recorded the result as neither confirmed nor refuted — which is why nothing false was published, but the pass cost a session and ended where it started. The third pass fixed the instrument BEFORE re-running anything, and the same intervention then produced an unambiguous verdict in two runs.
recommendation: Before running an experiment, write down what a negative result would mean under your instrument. If 'no change' is consistent with both 'my hypothesis is wrong' and 'my instrument cannot resolve this', the instrument is not yet good enough and the experiment is not worth running. Prefer the metric with a defined zero over the one that is merely available — retained bytes after a forced collection over working set, a row count over a process size, a captured artefact over a wall-clock duration. Then run the SAME instrument over baseline and intervention.
rationale: `LL-013`'s remedy protects against a scan with no subject; this protects against a scan whose subject is real but whose resolution is too coarse to answer the question. The failure is more dangerous because it produces a NUMBER rather than a silence, and a number that does not move reads as evidence of absence to everyone downstream. It is `LL-009`'s trap displaced by one step: there, two instruments agreeing were one instrument; here, one instrument answering was no instrument.
kind: improve
category: verification
impact_if_followed: An experiment either produces a verdict that survives, or is not run — and the register never acquires a REFUTED that rests on an instrument's blindness, which is the entry that closes a live lead permanently and invisibly.
impact_if_ignored: A correct hypothesis is discarded on a null result the instrument could never have produced differently, and the investigation moves on with the door closed behind it. `DEF-056`'s vacuous control with the sign flipped: there a control passed over nothing, here a refutation rests on nothing.

LL-048 [lessons]

id: LL-048
title: A root-path tool names A path, never THE cause — and when the retention is structural, removing the suspect it names by name changes nothing, which is the tell that enumeration cannot terminate.
statement: SOS `gcroot` printed a path into a leaked object that ran through `DefaultPartitionedRateLimiter.RunTimer` — a named, plausible, project-owned suspect, sitting exactly where a cause belongs. REMOVING IT CHANGED NOTHING: 20 of 20 objects still rooted, retention 141 MB to 150 MB. Stripping every OpenTelemetry registration, the other named suspect, cut retention by a third and ALSO freed zero objects. The tool's own footer said what the path did not: `Found 505 unique roots`. THE STRUCTURE WAS THE CAUSE — an `ExecutionContext` captured during host startup, reachable from process-global state, so every long-lived thing started at startup roots the same graph and no single removal can end the enumeration. A path is a witness that the object is reachable; it is not a claim that it is reachable ONLY that way.
context: 2026-09-02, `DEF-109` third investigation pass (`PE-771`). The `gcroot` output was persuasive enough that writing 'the rate limiter's timer is the cause' straight off it would have felt like reading the answer rather than guessing it. Two bisects, each cheap, converted a persuasive path into a measured non-cause; the variable that actually isolated was the COUNT of hosts, which no root path mentions.
recommendation: Read the path-count before the path. If a rooting tool reports many unique roots, treat any single printed path as one witness among many and do not attribute cause to a name in it without removing that name and re-measuring. When two independent removals each fail to free the object, stop enumerating suspects and switch to varying the QUANTITY of the leaking unit — the number that changes retention is the diagnosis, and it will not appear in any root path.
rationale: The value of a root path is that it proves reachability and shows the mechanism's shape; its danger is that it hands you a specific, checkable-looking name at exactly the moment you want one. `LL-029` says only an intervention that isolates a variable explains — a printed path is a reading that FITS, which is the category `LL-029` exists to refuse, and it is unusually convincing because a tool produced it.
kind: improve
category: verification
impact_if_followed: A named suspect is falsified in one cheap bisect instead of becoming the recorded cause, and the investigation reaches the structural variable rather than stopping one plausible name short of it.
impact_if_ignored: A defect row acquires a confident cause with a real stack path as its evidence, a remedy is built against it, and the remedy changes nothing — after which the row is harder to reopen than it was before, because it now reads as diagnosed.
